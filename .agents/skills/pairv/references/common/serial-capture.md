# 串口识别与运行证据

终端、驱动和基础串口操作见 [项目 README](../../../../../README.md)。需要程序化采集时，用当前可导入 pySerial 的解释器执行 `python -m serial.tools.list_ports -v`；命令名按本机环境调整。以下保留采集证据所需约束。

1. 按枚举的 USB 元数据确认唯一端口；元数据缺失或多匹配时先确认设备身份。Linux 可使用 `/dev/serial/by-id/` 的稳定链接；Windows 使用枚举得到的 COM 端口。不保存个人设备序列号为技能默认值。
2. 检查应用与 BSP 是否覆盖波特率；当前 EvalSoC 默认 3000000。端口权限、驱动或高波特率不受支持时，报告实际错误，不静默降速。
3. 在 `upload` 前打开读取器。让前台父进程管理读取器与上传子进程，或使用明确保持运行的串口工具；不要依赖执行环境可能回收的孤立后台进程。
4. 将收到的每个字节先追加到一份原始日志，再做文本/二进制解析；保留部分帧与退出尾字节。采集窗口需覆盖下载及预期运行时间，不以中途空读结束采集。
5. 看到启动 banner 后再解释应用结果。切换到 Host 二进制会话前消费启动文本、关闭监视器，避免两个读取器竞争 UART；事务期间不能混入文本日志。

记录固件 hash、端口身份、解析后的设备名、baud、构建参数与原始日志。设备标识和本机路径只保存在未提交的本地证据，发布前脱敏。

空日志且没有 banner 表示监视链路尚未证明，不能归因于芯片或 decoder。先确认读取器存活、波特率、连接和启动过程，再定位协议。INIT/SYNC 需相应 COMPLETE，数值正确另需输入及独立参考；不能以“已发送”替代。

异常后重新编程 RV 不等于整条芯片/NoC 链路已复位。按板卡流程恢复，记录实际复位范围；完整断电后恢复也不能单独证明 FIFO、握手或时钟的具体根因。

报告性能时同时保存 CPU Frequency、cycles 与换算时间，并明确采集/测量边界。
